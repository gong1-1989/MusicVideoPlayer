# MusicVideoPlayer 死代码清理与代码精炼审查

- 审查日期：2026-11-25
- 审查基线：`master` / `4a16f8a`（`修复 HLS 切换备用线路后不缓存不下载`，工作区干净）
- 审查范围：`src/` 140 个 `.cpp/.h`，33,384 行；`tests/` 4 个文件，8,316 行
- 审查方式：全库文件盘点、CMake 源清单比对、编译告警配置核对、类方法/自由函数调用扫描、私有字段引用扫描、`.ui` 对象名交叉核对、跨文件重复代码块扫描
- 实施状态：**审查后已按阶段 A 落地**，删除 7 项零调用接口，抽取 `HtmlText` / `MediaExtensions`，并统一 HTTP URL 判断；构建通过，全量测试 4/4 通过。
- 工具限制：本机未安装 `clang-tidy`、`cppcheck`、`ctags`，因此结论来自源码级静态扫描；Qt 元对象、`.ui` 自动连接和模板实例化路径做了人工排除，但不等价于编译器级死代码分析。

## 一、总体结论

**真正“零调用”的死代码很少，约 7 项、几十行；项目里更大的问题是同一套规则被复制到多个模块，形成行为漂移风险，而不是大量废弃文件。**

| 检查项 | 结果 |
|---|---|
| 源文件是否都参与构建 | 是，`src/` 下 67 个 `.cpp` 全部在 `CMakeLists.txt` 中，无孤儿源文件 |
| 私有成员字段是否完全未使用 | 未发现，`m_*` 字段均有声明外的读写 |
| `.ui` 控件是否完全无代码引用 | 未发现，所有 `objectName` 在 `src` 内都有引用 |
| 编译器未使用告警 | 目标启用了 `-Wall -Wextra`，上次基线构建无新增告警 |
| 真正无调用的类方法 | 1 个普通方法 + 5 个访问器 |
| 真正无调用的自由函数 | 2 个（同一已移除功能的读写接口） |
| 主要重复实现 | HLS 解析、媒体后缀、HTML 实体、URL 判断、下载三段分块拷贝 |

建议不要把“大规模拆分 `StreamProxy` / `DownloadManager` / `DownloadTask`”混进这次死代码清理。它们是结构性重构，回归面远大于删几个零调用 API，应单独立项、单独验收。

## 三、P1：优先去重的重复实现

### 3.1 HLS 播放列表解析：`DownloadTask::parsePlaylist()` 与 `HlsPlaylist`

**位置**

- `src/download/DownloadTask.cpp:828-1147`，单函数 320 行。
- `src/stream/HlsPlaylist.cpp:44-...` 的 `parse()`、`:211-...` 的 `variants()`。
- 重复片段：
  - `#EXT-X-BASE`：`DownloadTask.cpp:929-945` 与 `HlsPlaylist.cpp:68-82`
  - `#EXT-X-BYTERANGE`：`DownloadTask.cpp:999-1024` 与 `HlsPlaylist.cpp:85-105`
  - 主列表 BANDWIDTH 选择：`DownloadTask.cpp:843-910` 与 `HlsPlaylist.cpp:211-260`

**问题**

两套解析器各自维护 BASE、BYTERANGE、master 行序和 URI 解析规则。当前行为看似一致，但只要上游出现新的标签组合，很容易只修一处、漏另一处。下载链路还额外需要 AES `EXT-X-KEY`、`EXT-X-MAP` 和分片序号，所以不能简单让 `DownloadTask` 直接调用 `HlsPlaylist::parse()`。

**建议**

1. 先给 `HlsPlaylist` 增加“带分片元数据”的解析结果：`Segment { QUrl url; QByteArray range; HlsKey key; bool initSegment; }`，并保留现有 `Info` 接口不变。
2. `DownloadTask::parsePlaylist()` 改为消费共享解析结果，只保留“无 ENDLIST 是否允许快照下载”和“AES key 获取”两类下载特有逻辑。
3. 先补回归：`#EXT-X-BASE`、`#EXT-X-BYTERANGE`、`EXT-X-MAP + BYTERANGE`、AES-128 显式 IV、默认 IV、master 最高码率选择。
4. 风险：中高。不要在删死代码的同一个提交里做。

### 3.2 媒体后缀列表：至少 5 处各自维护

**位置**

- `src/cache/MediaCache.cpp:29-35`：磁盘缓存安全后缀
- `src/download/DownloadPaths.cpp:133-143`：下载目录影视/音乐后缀
- `src/download/DownloadTask.cpp:1903-1911`：媒体内容识别
- `src/ui/SearchPanelController.cpp:322-330`：粘贴直链后缀
- `src/ui/SearchPanelController.cpp:848-853`：直链按音频/视频分类
- `src/ui/MainWindow.cpp:914-917`：本地音乐无损后缀（不同类别，但可并入统一表）

**问题**

同一组扩展名在多个文件里手工维护，且已经出现差异：`mpd` 只在搜索直链列表里，`m4s/oga/avi/wmv/mpg/mpeg` 只在下载识别列表里，`wma` 只在下载路径列表里。后续新增格式很容易出现“能识别不能下载”或“能下载不能识别”。

**建议**

新增 `src/util/MediaExtensions.{h,cpp}`，按用途暴露：

- `isKnownAudioSuffix()`
- `isKnownVideoSuffix()`
- `isKnownMediaSuffix()`
- `isDirectLinkSuffix()`（包含 `mpd`，保持搜索侧现状）
- `isLosslessAudioSuffix()`

保留各调用点原有集合语义，不强行合并成一个“大而全”列表。先做纯函数与单元测试，再逐个替换。

### 3.3 HTML 实体解码：三套实现

**位置**

- `src/net/MaccmsWebProvider.cpp:71-114`：最多两轮，处理 `&nbsp;`，带数字实体
- `src/ui/SearchPanelController.cpp:343-377`：一轮，带数字实体，不处理 `&nbsp;`
- `src/net/ConfigMapper.cpp:190-202`：只处理常见命名实体，不做数字实体

**问题**

数字实体的 `globalMatch + 捕获 + fromUcs4` 循环在 Maccms 和 SearchPanel 中几乎逐行相同。两处轮数和 `&nbsp;` 行为不同，后续修 XSS/编码问题时很容易只改一处。

**建议**

新增 `src/util/HtmlText.{h,cpp}`：

```cpp
QString decodeEntities(const QString &raw, int maxPasses = 1, bool decodeNbsp = false);
QString stripTags(const QString &raw, int maxPasses = 1, bool decodeNbsp = false);
```

调用点显式传参，保持现状：

- Maccms：`maxPasses=2, decodeNbsp=true`
- SearchPanel：`maxPasses=1, decodeNbsp=false`
- ConfigMapper：可只使用 `stripTags(..., 1, true)`，但注意它当前不做数字实体，若统一后要补测试确认没有把正文里的 `&#...;` 意外还原。

回归用例至少覆盖：`&amp;#39;` 双重转义、`&#x4E07;`、`&#39;`、非法代理区码点、`&nbsp;`。

### 3.4 URL 合法性判断：已有公共函数却没有统一使用

**已有实现**

- `src/util/NetworkAddressPolicy.h:26` 的 `isHttpMediaUrl()`：要求 `QUrl` 有效、host 非空、scheme 为 http/https。

**重复位置**

- `src/download/DownloadTask.cpp:56` 的局部 `isHttpUrl()`（未检查 host）
- `src/net/HttpClient.cpp:64` 的 `isAllowedScheme()`
- `src/ui/DownloadController.cpp:72-73`、`:77-78`：同一函数里两次 scheme 判断
- `src/net/MaccmsWebProvider.cpp:439-441`
- `src/net/ExternalSearchProvider.cpp:52-53`
- `src/stream/HlsPlaylist.cpp:263-264`
- `src/ui/SearchPanelController.cpp:335-340`
- `src/net/ConfigMapper.cpp:231-232`

**建议**

统一改用 `NetworkAddressPolicy::isHttpMediaUrl()`，删除局部副本。

**注意行为差异**：`DownloadTask::isHttpUrl()` 当前不要求 host 非空，改成 `isHttpMediaUrl()` 会拒绝 `http:///path` 这类异常 URI。按 HLS 规范这本来就无效，属于收紧而不是破坏；但要补一条“host 为空的分片地址被拒绝”的测试，避免把兼容行为改掉却没人知道。

### 3.5 `DownloadManager` 三套分块复制流程

**位置**

- `publish`：`startPublishCopy()` `:1897`、`copyPublishChunks()` `:1941`、`cancelPublishCopy()` `:2027`
- `seed`：`startSeedCopy()` `:2050`、`copySeedChunks()` `:2099`、`cancelSeedCopy()` `:2199`
- `cache`：`startCacheCopy()` `:2224`、`copyCacheChunks()` `:2289`、`cancelCacheCopy()` `:2404`
- 合计约 570 行，三个定时器、三组 `QHash<QString, QFile*>`、三套取消/失败/完成分支。

**差异**

- seed：只复制播放缓存前缀到暂存半成品，完成后继续网络下载，不发布。
- cache：从已有偏移复制播放缓存到下载半成品，完成后发布到最终文件。
- publish：把暂存完整文件跨盘复制到下载目录的 `.mvpdownload`，完成后改名并清理暂存目录。

**建议**

先抽一个不改变行为的 `ChunkCopyJob` 数据结构，统一 source/target/remaining/mode/finalPath/stagingDir；三个 `copy*Chunks` 仍保留入口，但内部走同一个 `pumpChunks()`，完成回调按 mode 分派。这样先消掉重复的读写/失败/取消骨架，再考虑合并定时器。

**风险**：高。涉及跨盘发布、断点续传、失败回滚、暂存清理和 UI 状态通知。建议放在 P0/P1 纯函数去重之后，单独提交、单独跑下载集成测试。

## 四、P2：结构性精炼，不建议混入本次清理

### 4.1 `StreamProxy` 的缓存状态标志过多

`StreamCacheEntry` 同时用 `pending`、`upstreamStarted`、`complete`、`failed`、`transient`、`prefetch`、`multiRange` 等布尔值表达状态；`startUpstreamRequest()` 单函数 388 行。这里不是死代码，而是状态机可读性问题。

**建议先用低成本手段收敛**：

- 抽出 `isUsableCache()`、`isPendingPlaceholder()`、`isMultiRangeActive()` 等谓词，先把条件表达式统一。
- 把磁盘完整文件命中、半截文件前缀切片、网络回源三段拆成私有函数，减少 `startUpstreamRequest()` 的局部变量和捕获列表。
- 暂不做 `EntryState` 枚举全量替换；布尔值之间有正交维度，贸然枚举化容易改变并发语义。

### 4.2 `DownloadTask` 体量偏大

1,838 行，`parsePlaylist()` 320 行，直链下载、HLS 解析、AES 解密、续传指纹、HTTP 状态都在一个类里。

**建议顺序**：

1. 先做 3.1 的 HLS 解析共享，`parsePlaylist()` 会自然缩小。
2. 再把 HLS 分段状态抽成内部 `HlsDownloadSession`，`DownloadTask` 只保留直链/统一生命周期。
3. 不改变公开 API，不改 `DownloadJob` 持久化字段。

### 4.3 `SourceProbe` 的候选探查函数过长

`probeNextCandidate()` 286 行，混合了候选预算、HTTP 分类、JSON 数组评分、字段选择、Subsonic 特例和建议配置组装。

**建议**：

- 抽出 `classifyReply()`（HTTP/XML/JSON/未授权分类）。
- 抽出 `buildSuggestedConfig()`（字段选择和建议源组装）。
- 保留 `Prober` 的候选顺序和预算逻辑不变。

### 4.4 HTTP 回调样板代码

`reply->abort(); reply->deleteLater(); return;` 在多个模块重复约 20 处。可加 `HttpClient::discardReply(QNetworkReply *)`，但这属于可读性优化，收益小于 3.1-3.4，放在最后。
